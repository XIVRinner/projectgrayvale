# Product

## Register

product

## Users

GrayVale primarily serves server/community operators plus players using a desktop browser game shell. Their core context is server-connected play: joining servers, registering characters, using chat, managing social surfaces, and operating admin or moderation workflows when authorized.

Secondary audiences, such as solo developers, local testers, and early RPG players, may use separate documents when a task specifically targets them.

## Product Purpose

GrayVale is a data-driven RPG game shell with multiplayer/server-connected systems. The product UI should make server state, character identity, chat, moderation, and profile registration feel trustworthy and explicit while preserving the atmosphere of an arcane fantasy world.

Success means players understand which character and server are active before meaningful server actions occur, and operators can perform admin/moderation tasks without ambiguity or decorative friction.

## Brand Personality

Arcane, precise, dependable.

The UI should feel like a reliable control surface inside a fantasy world: ritual-like enough to belong to GrayVale, precise enough to trust with identity and server state, and restrained enough that gameplay and operational tasks remain legible.

## Anti-references

Avoid neon cyberpunk MMO noise, excessive glow, unreadable fantasy chrome, and decorative effects that make server/admin workflows feel less trustworthy.

Avoid treating product surfaces like generic fantasy posters. The interface can be atmospheric, but controls, status, and consent points must stay clear.

## Design Principles

1. Server state must feel explicit and consent-driven. Joining, switching, registering, or reconnecting should never feel silent or accidental.
2. Fantasy atmosphere should support clarity, not compete with it. Visual texture is welcome only when labels, actions, and states remain immediately readable.
3. Admin and moderation tools must feel sober and reliable. Prioritize unambiguous controls, stable layouts, and clear consequences.
4. Use compact progressive disclosure for complex systems. Keep the base layout terse, and move explanations into details, hints, or secondary panels.
5. Prefer consistent product patterns over decorative novelty. Familiar dialogs, forms, lists, and confirmations are affordances, especially in server and identity flows.

## Accessibility & Inclusion

Target WCAG AA where practical. Dialogs and forms should be keyboard usable, focus states should be visible, reduced-motion preferences should be respected, and color should not be the only cue for status or severity.
